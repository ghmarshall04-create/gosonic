# SonicBlast Smart Launcher security model

## Hard boundaries

- SonicBlast is non-custodial. Wallet connection returns only a public address; signing and transaction approval occur inside the user’s wallet.
- The Worker never receives a recovery phrase, seed phrase, private key, wallet password, raw signing key, RPC signing credential, or browser wallet session secret.
- xterm.js is a local browser display and command parser. It supports fixed `help`, `status`, `connect`, `script`, `deploy`, `pair`, and `clear` actions only. It cannot execute arbitrary Bash, run a server process, load remote scripts, or accept remote shell commands.
- Token deployment uses an embedded, reviewable `SonicBlastFactory` artifact and a user-approved `eth_sendTransaction` call.
- Chain scripts never call a Worker quote/launch endpoint, 0x, an aggregator, or an API-key-backed quote service. Wallet-routed `eth_call`, `eth_getCode`, `eth_getTransactionReceipt`, and `eth_sendTransaction` communicate with the selected chain.
- Pairing and direct SNBL buying use only router, asset, wrapped-native, and route addresses embedded in `public/network-config.js`. Browser fields and xterm commands cannot choose an arbitrary router or execution target.
- The Worker does not sign transactions or custody cryptocurrency.

## Wallet connection behavior

- Connection requests occur only after the visitor presses a connect, deploy, pair, or direct-buy control.
- The app listens for account and network changes and updates the visible address; it does not persist wallet credentials.
- The app switches only to the selected/configured EVM network. If the wallet does not know that network, the user must add or select it inside their wallet.
- The mobile fallback opens SonicBlast in MetaMask’s own mobile browser. It does not ask the visitor to type any wallet secret.

## Transaction safeguards

- Token creation is fixed-supply with no owner-only minting, transfer tax, blacklist, pause, or upgrade controls in the included source.
- The factory has no owner, fee, custody, or privileged parameter; anyone can use it to deploy the same fixed-supply token implementation.
- Before the app calls a configured factory or V2 router, it asks the connected wallet for its chain code. A missing-code result stops the script.
- Pairing calculates a 20-minute deadline and applies the reviewed `slippageBps` setting to minimum amounts. It asks for exact approvals, not unlimited approvals.
- Direct SNBL buying first reads `getAmountsOut` from the reviewed V2 router, validates the returned route and input amount, and builds a fresh 20-minute exact-input swap. Pool reserves can change; the minimum-output amount and wallet confirmation are the protection boundary.
- The app requires the connected wallet to be the designated initial token owner before it can pair the first liquidity.
- The wallet confirmation screen remains authoritative. Users must independently check chain, factory/router, contract addresses, route, recipient, amounts, minimums, deadline, gas, and transaction value.

## Configuration safeguards

- Treat `public/network-config.js` as an allowlist, not a user settings surface. It contains public addresses only and requires redeployment for changes.
- Verify the selected router supports the exact V2 function signatures used by the scripts before mainnet use.
- Verify `wrappedNative`, payment asset, SNBL token, and every optional route intermediate against trusted official sources. A wrong public address can still direct a valid wallet transaction to the wrong contract.
- Do not configure a route wider than the assets you have reviewed. The direct script allows 2–5 addresses and rejects adjacent duplicates.

## Board and social controls

- A board entry becomes `live` only after its submitted token address and HTTPS market URL pass validation.
- A creator browser receives a random management capability; the registry stores only a hash. This is not a user identity or financial authorization system.
- Community heat is not a trading signal, due-diligence score, or proof of legitimacy.
- Chat and WebRTC media use rooms and signaling only. Add authentication, moderation, rate limits, and abuse controls before public-scale use.

## Mainnet release checklist

1. Have an independent Solidity/security professional audit the token, factory, generated bytecode, direct V2 script builder, and exact V2 router integration.
2. Test all deployment, approval, pairing, and direct SNBL swap paths on the intended testnet first.
3. Verify every public address in `public/network-config.js` against trusted official sources and deployed bytecode.
4. Confirm legal, disclosure, taxation, consumer-protection, sanctions, liquidity, and licensing requirements that apply to your launch and jurisdiction.
5. Keep the Worker’s TURN secret isolated from all wallet or chain-related configuration.

## Never collect a phrase

A recovery phrase must never be submitted to SonicBlast, a Cloudflare Worker, a form, xterm.js, email, chat, or support. If a wallet needs recovery, it must happen only inside that wallet provider’s official application.
